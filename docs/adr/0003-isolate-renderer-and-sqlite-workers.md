# ADR 0003：隔离renderer并在主进程监管的worker中运行SQLite

- 状态：已接受
- 日期：2026-07-29
- 决策者：项目维护者

## 背景

应用需要在macOS窗口关闭后继续采集，同时处理WebSocket心跳、每秒数百条事件写入、历史搜索和实时界面刷新。

如果把采集或数据库放在renderer中，窗口隐藏、重载或崩溃会破坏任务生命周期，并扩大页面脚本能访问的权限。如果把同步SQLite写入和大查询直接放在Electron主线程，数据库抖动可能延迟心跳、窗口事件和退出流程。

## 决策

采用以下边界：

1. Electron主进程拥有采集状态机、协议连接、窗口、托盘、退出协调和实时投影。
2. SQLite由主进程监管的两个Node worker执行：
   - writer worker持有唯一可写连接。
   - reader worker持有只读连接并执行白名单查询。
3. renderer启用`sandbox`和`contextIsolation`，关闭Node集成，只通过preload公开的版本化窄接口访问能力。
4. renderer不能获得通用IPC、SQL、文件路径、上游临时凭据、原始UID或本地HMAC用户键。
5. 实时界面只展示已经完成SQLite事务提交的事件。

## 理由

- 主进程生命周期独立于窗口，适合拥有长期采集任务。
- writer worker把同步SQLite工作从Electron事件循环移走，避免心跳和界面生命周期被磁盘操作阻塞。
- reader worker把历史搜索与写入隔离，查询故障可以独立恢复。
- 窄preload接口降低renderer被恶意上游文本或前端依赖攻破后的权限。
- 提交后再展示使界面与持久化真相一致。

## 后果

正面影响：

- 窗口关闭或renderer崩溃时采集仍可继续。
- 数据库卡顿不会直接阻塞Electron主线程。
- IPC和数据泄露面更小。
- 写入、读取和界面刷新可以分别做背压与故障恢复。

代价：

- 需要维护主进程与两个worker之间的消息协议。
- 必须处理worker崩溃、迟到响应和有界队列。
- renderer模型需要单独的只读视图类型和运行时schema。
- 实时事件会比网络接收时间晚一个数据库批次，目标上限约100至250毫秒。

## 被否决方案

### 在renderer中运行采集和SQLite

窗口生命周期不稳定，且需要赋予renderer过高权限，因此否决。

### 所有工作都在Electron主线程执行

实现简单，但同步SQLite提交和历史查询可能阻塞心跳、窗口和退出流程，因此否决。

### 每个功能模块各自打开可写连接

会引入写竞争和难以验证的事务顺序，也破坏唯一写入者约束，因此否决。

### 把整个采集器放入独立子进程

隔离更强，但第一版会增加部署、进程监管和跨进程状态同步成本。当前协议解码和心跳是异步任务，先保留在主进程；如果后续压测证明CPU解压会阻塞事件循环，再单独提交ADR调整。

## 复审条件

出现以下任一情况时重新评估：

- protover 3解压在目标吞吐下造成主进程事件循环延迟超过验收阈值。
- 需要同时采集多个直播间。
- 历史分析成为长时间CPU任务。
- Electron安全模型或Node worker支持发生不兼容变化。

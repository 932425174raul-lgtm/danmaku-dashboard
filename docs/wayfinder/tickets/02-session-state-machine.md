## Question

等待开播、连接中、采集中、短暂断线、数据缺口、主动停止、正常下播、风控失败和异常中断之间如何转换；每个状态允许哪些用户操作、何时创建或结束历史会话、哪些转换需要持久化，才能保证后台运行和应用重启后的行为一致？

## Resolution

状态机由Electron主进程唯一持有，运行状态包括空闲、房间解析、等待开播、初次连接、采集中、连接恢复、匿名风控、启动失败和停止中。

- 首次WebSocket鉴权成功后才创建采集会话，等待开播或初次连接失败不生成空历史。
- 关闭或最小化窗口不改变采集状态，切换直播间必须先结束活动会话。
- 活动会话断线后打开一个连续数据缺口，轮换节点并自动恢复；同一离线区间不会因多次重试拆成多个缺口。
- 匿名风控在初次连接阶段不创建会话，在连接恢复阶段保留会话和缺口，并使用较慢的有上限退避。
- 用户停止、确认下播和应用正常退出都执行有序刷新，分别记录结束原因。
- 活动会话每10秒写入检查点。应用崩溃后，下次启动把残留会话标记为异常中断，不自动连接原直播间。
- 开始、停止、连接成功、缺口和终态转换都必须幂等，旧运行代次的异步回调不能改变新状态。

完整状态、转换、持久化边界和12个验收场景见[采集会话状态机](../../spec/session-state-machine.md)。
